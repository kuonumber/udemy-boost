# ADR 0009: 三個同步檔各用不同的合併策略

日期：2026-09-11　狀態：已採納

## 脈絡

Phase 6 要把 `watch-log.csv`、`notes.md`、`progress.md` 同步到 Google Drive，兩台電腦都能編。
一開始的直覺是「找一套通用的合併」，但這三個檔的性質完全不同：一個是機器追加的不可變記錄、
一個是人手寫的內容、一個是前者算出來的報表。用同一套規則一定有人受害。

## 決策

| 檔案 | 策略 | 理由 |
|---|---|---|
| `watch-log.csv` | 集合聯集（grow-only set），身分＝正規化後的整列 | 每列寫出後不可變 → 天生無衝突。合併可交換且冪等，兩台同時看課也不會互相覆蓋 |
| `notes.md` | entry 級合併：同 id 取 rev 新者；rev 相同但內容不同 → 兩則都留並標 `ub:conflict` | 手寫內容，弄丟一個字都不行。寧可留下需要人工處理的衝突，也不替使用者挑 |
| `progress.md` | localWins：本機有檔就以本機為準，本機沒有才下載 | 它是 CSV 的衍生物。合併兩份分析報告只會產生垃圾；正解是同步完 CSV 後在本機重算再推上去 |

同步順序因此被固定為：**CSV 合併 → 播放頁重算 progress.md → 推 progress.md**。
反過來會把舊資料算出來的報告推上雲。

舊格式的 notes（只有 `<!-- lecture:N -->`）以「lectureId + 內容」決定性地算出 id，
確保兩台機器對同一則舊筆記算出相同 id，不會在合併後變成兩則。

## 替代方案

- **全部用 last-write-wins**：最簡單，但會直接弄丟另一台寫的筆記。否決。
- **全部用三方合併（3-way merge）**：需要共同祖先，等於要在本機保存每個檔的 base 版本；
  對 CSV 是多餘的（聯集就夠），對 markdown 的行級合併也會產生難看的衝突標記。成本高於收益。
- **progress.md 也做內容合併**：兩份報表的章節統計數字交錯合併，結果沒有任何意義。否決。

## 後果

- 每加一種要同步的檔案，都必須明確指定策略；orchestrator 的 spec 以 `merge` 函式或
  `localWins` 旗標表達，不給預設值以外的模糊地帶。
- notes 的衝突需要人工處理，popup 會回報「有 N 則衝突待人工處理」。
- 合併函式各自回報自己的統計（CSV 的 `bad`、notes 的 `conflicts`），orchestrator 原樣往上帶。
